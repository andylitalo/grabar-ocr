## Question

Which OCR engine reads *this* book best, line by line, on verified line crops? Every
CER in the repo so far is from *Ժամագիրք Ատենի*; this is the first measurement on the
Տօնացոյց.

## Method

1. **Same pixels for everyone.** `export_crops.py` writes each test line's crop with
   `dev/line_review/crops.line_crop` (the crop the human transcribed from) to
   `runs/ocr_eval/crops/<line id>.png`. Every engine reads those files.
2. **Predict on every sampled line, score the transcribed ones.** Each engine runs once
   over all of `sample.json`'s picks, so scores update as transcription continues without
   re-running engines. Output: `data/ocr_predictions/<engine>.json` (committed),
   `{engine, settings, generated_at, lines: {line id: text}}`.
3. **Score** (`score.py`, `jiwer`): character error rate per engine, pooled over lines
   (total edits / total reference characters). Before comparing, both sides are NFC
   normalized, whitespace is collapsed, and look-alike punctuation is folded
   (`-`/`֊`/`‐`, `.`/`․`, `:`/`։`, Phase 10's rule). Raw (unfolded) CER is reported too.
   Lines marked `illegible` or `bad-crop` are skipped. A third column ignores whitespace
   entirely: spacing around punctuation is ambiguous on this print (Gemini Pro writes
   `Բ . 11 .` for `Բ. 11.`).
4. **Breakdowns:** per stratum (`vol1-body`, `vol2-body`, `display`, `drop-cap`), and
   lines with vs. without the abbreviation mark ՟ (Phase 2b found a 3× gap there).
5. **Uncertainty:** a 95% bootstrap interval over lines for each CER. With tens of lines,
   intervals will overlap; the table says so rather than ranking on noise.
6. **Noise floor:** once rechecks exist, the CER between the two human passes. Engine
   differences smaller than it don't count.
7. **Report:** `reports/phase11_ocr_comparison.md`, regenerated by `score.py`: the table,
   the breakdowns, and the worst lines per engine for error analysis.

### Ceiling of the Calfa engines (2026-10-08, sample built, typing under way)

The 12-line result (both 0%) was the luck of a small, easy sample. Both engines were run
on **every line of the book** (14,388 lines; verified lines where they exist, otherwise the
`paddle-filled` baseline with fixes so far): `dev/ocr_eval/ceiling.py`.

- **They disagree on 36.6% of lines** (5,264), **2.2% of characters**. Only 94 differ just
  in spacing. The rest are look-alike Bolorgir letters: Չ/Ձ/Զ (600+, mostly large line
  initials), չ/շ, զ/ղ, է/ե, գ/դ, and `3` or `)` for ձ. Where they disagree, at least one is
  wrong, so **their line error rates sum to at least 36.6%** and their CERs to at least
  about 2.2%: roughly 1–2% CER each, i.e. an error every few lines, not a near-perfect
  read.
- **Sample** (`data/transcriptions/ceiling/sample.json`, served at `/transcribe?set=ceiling`):
  300 random disagreements + 200 random agreements, 164 pages, half Vol I, half Vol II.
  Each engine's line error rate = the two groups' rates weighted by their share of the
  book; lines-per-error is its inverse, with a bootstrap interval
  (`reports/phase11_ceiling.md`). Agreements also catch identical mistakes by both.
- Test-set transcriptions of verified lines are reused, not retyped. Lines from
  unverified pages carry baseline keys (`p520~line_013`), not stable ids; a box that clips
  the text is marked Bad crop and left out.

### LLM correction of the Calfa output (2026-10-09, built; awaiting typed lines)

Target (maintainer): **> 90% of lines error-free**; below that, correcting lines costs
more than typing them. Phase 5 found Gemini 3.1 Pro the best and cheapest corrector and
Opus comparable, with GPT-5.5 over-correcting and strict rules essential.

`dev/ocr_eval/correct.py` sends each page with **both engines' readings** where they
disagree (`A: … ‖ B: …`) and one reading where they agree, under Phase 5's v2 rules
adapted to two readings. Candidates: `claude-opus-5-5`, `gemini-3.1-pro-preview`,
`gemini-3.8-flash`, `gpt-6.1-sol` (Gemini 4 wasn't reachable with this API key yet:
`gemini-pro-latest` still serves 3.1 Pro; see "Gemini 4 check" below for the later run). Opus calls carry the server-side refusal
fallback (`fallbacks: "default"`, sent via `extra_body`: the repo's anthropic SDK 0.107
predates the parameter).

Smoke test on p.615 (86 lines, 42 with two readings): all four parse cleanly and agree
on the clear cases (`ԴՁՉ`/`ԴՁ` → `ԴՁ`, `Գչշ`/`Գշ` → `Գշ`, `բ)`/`բձ` → `բձ`); Opus, Gemini Pro
and Flash change no agreed line, GPT 6.1 changes 2. Per page: Opus 26 s (~$0.08),
Gemini Pro 33 s, Flash 11 s, GPT 6.1 31 s.

Scoring (`ceiling.py score`) rates every engine, correctors included, by error-free
lines weighted back to the book, with a bootstrap interval and a count of lines a
corrector broke (both OCR engines right, corrector wrong).

v4's own predictions didn't change. Its interval in the report moved to 91.3–98.1% only
because the bootstrap draws from one random stream across the engines in file order, so
more lines in other rows shift it. To stop this happening again, `common._write`, which
every engine, corrector and `+rules` file goes through, now never deletes a prediction: a
line that a rewrite drops, or replaces with a different reading (`--redo`, a settings
change), moves to `stale` (`common.set_aside`). Each entry says when it was last saved
(`predicted_before`) and, only when that is known, which settings made it (`settings`, an
id into `stale_settings`): a file marks `uniform_settings` only when every line in it came
from its `settings`. Files made before this (all of today's) don't, because `correct.py`
used to keep corrections from earlier runs under the latest run's settings (v2, v3 and v4
were each built over 3–5 runs on 2026-10-09), so their entries carry no settings rather
than possibly wrong ones. A difference only in spacing or Unicode composition isn't a
different reading (no score sees it) and isn't kept. One process writes a predictions file
at a time (a lock; `migrate repair` takes them all first). Ctrl-C during a run or
`correct.py` cancels the calls not sent yet and still saves the ones in flight; a second
Ctrl-C abandons those, with a warning.

#### Planned: review buckets (maintainer, 2026-10-09)

Every line will still go to a human for final review. The pipeline sorts lines into
buckets so the reviewer can move quickly through the likely-correct ones and spend
attention where the machine is least sure. Candidate signals:

- **likely correct**: both engines agree and the corrector left the line unchanged;
- **possible error**: the engines disagree and the corrector chose one reading, or the
  corrector changed an agreed line;
- **likely error**: the corrector's output matches neither reading, or it changed more
  than one or two letters, or the line has a low-confidence stratum (display type, drop
  cap, bad crop).

Each bucket's actual error rate is measured on the typed ceiling lines before the
thresholds are trusted. Not built yet. When the OCR + v4 run happens, log each line's
signals (engines agree?, which reading v4 chose, v4 changed an agreed line?, risk pattern
hit?) so buckets can be assigned and measured without re-running anything.

#### v6 risk patterns, fixed in advance (2026-10-11)

v6 = v4 + a second, separate stage: the image of each *agreed* line that matches a risk
pattern, sent to the corrector with the page text, which is allowed to fix the flagged line
from the image. The patterns are fixed here, before the human corrections they'll be
tested on exist, so the v4-vs-v6 comparison can't be tuned to them. They match the
**Paddle reading** of the line (the agreed text):

#### Fallback lines: a re-ask, and no decision step (2026-11-25)

A line **falls back** when v4's answer can't be trusted for it: the answer misses the line,
echoes both readings, or holds text too far from both OCR readings (the drift check, meant
for a skipped row that shifts every later line onto the wrong number). It then keeps
Paddle's reading. In the re-run of 2026-11-23, 5 lines fell back on 103 pages, and a retry
on p508 dropped a row and shifted 54 lines (fixed: the better attempt is kept). Three
options were weighed (maintainer, 2026-11-24):

1. **JSON answers under a response schema (v4-json):** tried, not adopted. It scored no
   better than v4. The numbers, the reasons and how to reproduce them are in
   `experiments/v4_json/README.md`.
2. **Re-ask:** a line still misaligned after the page's retry is asked again on its own,
   with 3 lines either side for context; only its own answer is taken, under the same
   checks (`reask`, on by default; `--no-reask`). Built, together with telling the two
   kinds of fallback apart (below). Which lines fell back, and why, is now logged in
   `reports/phase11_correction_usage.json` (git-ignored: local only).
3. **A decision step** (a cheap model picks A, B or neither; Gemini corrects only
   "neither"): **not built.**
   - **Minimal benefit; it targets the wrong problem.** On the 163 typed lines, v4 picks
     between A and B correctly on 48 of 49 lines where one of them is right. Of v4's 6
     errors, 4 are lines where both engines agree on the same wrong reading, which a step
     that only sees disagreements can never reach (v4 fixes 2 of those 6 today, from the
     page around them).
   - **Scale:** about 5,000 separate requests over the book, one per disagreement, instead
     of ~190 page requests.
   - **Risk:** "neither" is 21% of disagreements (13 of 62), and v4 gets 12 of those 13
     right using the whole page's text; corrected line by line, they lose that context. It
     would also be a new pipeline, reopening the v4 decision.

**What the fallbacks really were.** v4 fell back on 4 lines that could be identified,
`p483.003`, `p508.011`, `p510.054` and `p520.023` (it kept Paddle's reading on each; its
fifth, on p550, wasn't recorded). They aren't misaligned answers: each is a display
heading that both engines read as nonsense (Paddle: `աթ, տն էսրոյն րիդորիԼու`), and
Gemini's answer is a plausible reconstruction (`Շաբաթ, տօն է սրբոյն Գրիգորի Լու-`), too
far from both readings for the drift check to accept. So the check is doing its job,
refusing a rewrite nothing can verify, and these lines need a person, not another request.
None is a typed line. In the v4-json run a re-ask of every fallback line was tried on
exactly these 4 lines and fixed none, and in v4's run the page retry fixed none either (on
p508 it made things worse). Asking again only helps a misaligned answer, and no first
answer in either run was misaligned; the one shift seen, p508's retry, was triggered by
the heading line.

**So the two kinds of fallback are now told apart** (`parse_reasons`). A line is
*misaligned* when the answer misses it, echoes both readings, or holds the text of a line
within 3 rows (a row dropped or repeated, the rest renumbered); only then is the page asked
again, and still-misaligned lines re-asked. A line whose answer is too far from its own
readings and its neighbours' is *too far*: it keeps the OCR, isn't asked again, and is
logged under `needs_review`. For the book-wide run, those lines go to the human review.
Checked three ways, 2026-11-25:

- **Unit tests** for each reason, and that a too-far line alone isn't asked again while a
  shifted answer is.
- **Offline, on real pages (no API calls):** v4's stored answers for the 103 pages, broken
  at 5 places a page by dropping a row (as on p508) or repeating one: every line after the
  break came out `shifted` (21,341 each way; the dropped case also leaves the last line
  `missing`), none `too_far`, none wrongly accepted, and every broken page was asked again.
  Gemini's 4 heading answers came out `too_far`, their pages not asked again. A shift of
  more than 3 rows would be called too far; none has been seen.
- **Live, on the 5 pages that had fallbacks** (about $0.40): 1 request a page, the 4
  headings flagged, p550 without a fallback this time. The old logic made 9-10 page
  requests plus 4 re-asks for the same pages.

#### Drop-cap lines: the body and the capital are read apart (decided 2026-11-26)

On a line that opens with a drop capital, the crop holds the whole capital, so the
engines read the text at a fraction of its size. With the capital taken out of the crop,
their disagreement on these lines falls from 13.9% of characters to 2.9% (other lines:
2.0%); the measurements are in `experiments/drop_caps/README.md`. Decided (maintainer):

- **The body text is read from a crop without the capital** (that experiment's `body`
  crop): both engines and the corrector read the body only.
- **The capital is read on its own.** Tesseract reads it first, from the line's crop as
  it is today; it got 103 of the 113 typed capitals that way, against 68 for Paddle. Then
  Gemini and/or other models read the capital's crop to confirm it. The capital gets its own
  status, apart from the body's: confirmed, or flagged for a person.
- **Which lines have a drop cap** is found from the ink, not only from review ops: 166 of
  the 372 found have no `initial` op, because the box-growing rule of 2026-11-17 took
  their capital into the line. A person's `initial` op, and the letter typed with it,
  always wins.
- **Before the book-wide run:** check that every drop cap is found. The detector misses
  most Հ capitals (their slanting stroke is short) and takes in 3 headings.

How the capital's readings and status are recorded, and how the corrector sees a line
whose capital is read apart, is settled when this is built. A proposal is in "Drop-cap
capitals: readings and status (proposed)" below.

#### Drop-cap capitals: readings and status (proposed)

- **The capital is its own field on the line**, not part of the body's text: a line's
  text is the capital's letter followed by the body. A wrong capital is then a one-letter
  fix, and the body's checks (engine agreement, the drift check) don't count it.
- **Each reader's capitals in their own predictions file**, keyed by line id like the line
  predictions: `{line id: letter}` per reader (Tesseract, Gemini, …), with `?` where a
  reader can't tell.
- **A status per capital**, resolved from those files:
  - `typed`: a person typed it (the `initial` letter in `data/verified_lines/`). It wins
    over every reader.
  - `agreed`: the readers agree.
  - `flagged`: they differ, or one can't tell. The capital goes to a person.
- **A flagged capital is its own task for a person:** its crop and the line, one key for
  the letter. It doesn't hold up the body's review, and a typed answer goes in as the line's
  `initial`, where the layout review already puts typed capitals.
- **The capital's box** comes from the detector, or from the `initial` op where there is
  one, and is recorded with the run's outputs, not in `data/verified_lines/` (which holds
  what review checked).

## Open OCR VLMs: feasibility (desk check, 2026-10-05)

Not run; from published benchmarks. **Armenian is the deciding fact, not model size.**

- **GlotOCR Bench** (2026; 100+ scripts, *rendered modern fonts*, not 1915 Bolorgir) on
  Armenian: Gemini 3.1 Flash-Lite 97% of sentences within 5% CER, dots.mocr 95%,
  dots.ocr 93%; **most open models ~0%, including Qwen3-VL-8B**, which hallucinates other
  scripts. That matches Surya here (Armenian read as look-alike Latin).
- **Leaderboards measure something else.** OmniDocBench and olmOCR-Bench are dominated by
  Latin/CJK documents; small specialists (PaddleOCR-VL-1.6, TeleOCR ~1B) beat
  Qwen3-VL-235B there, which says nothing about Armenian.
- **What fits this Mac (M1 Pro, 32 GB)** through MLX: dots.ocr/dots.mocr (~3B, ~6 GB bf16;
  `mlx-community/dots.mocr-bf16` exists), Qwen3-VL-8B (4-bit ~5 GB), Qwen3-VL-32B or
  Qwen3.6-35B-A3B at 4-bit (~18–20 GB, slow). What doesn't: Qwen3-VL-235B-A22B (~130 GB
  even at 4-bit: a multi-GPU cloud box or a 192 GB Mac Studio).
- **Qwen would need fine-tuning to be useful** (zero-shot ~0% on Armenian). The Manchu
  study (arXiv 2507.06761) took Qwen2.5-VL from ~25–30% to ~5–8% CER with LoRA on 1,000
  synthetic images, and it transferred to real documents. LoRA on a 7–8B model is a few
  GPU-hours on one rented 48–80 GB card; on this Mac, MLX LoRA is possible but slow.
- **Expected gain is narrow.** The Calfa engines already read clean body text at 0%
  here. A VLM can only help on what's left: display type, drop caps, abbreviations,
  damaged print, Vol II. Its language prior cuts both ways: it can recover damaged letters,
  but it also "fixes" spelling and case (Gemini's `եբր` for `Եբր`), which a literal corpus
  must not have.
- **dots.mocr was then run** (see Results): 12.3%, behind the Calfa engines. Decide on a Qwen fine-tune only if the full test set shows the Calfa engines
  failing on the hard strata.
