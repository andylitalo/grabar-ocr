# Phase 11 — OCR engine comparison on the Տօնացոյց

**Status:** harness built and run 2026-10-05; results provisional (test set growing) · **Created:** 2026-10-05 · **Owner:** —
**Depends on:** Phase 10's test set (`data/transcriptions/testset/`), which is still growing.
Until it reaches its gate (300 lines), every number here is **provisional**.
**Feeds:** the engine choice and the re-OCR of the corpus (`docs/backlog/README.md`).

## Question

Which OCR engine reads *this* book best, line by line, on verified line crops? Every
CER in the repo so far is from *Ժամագիրք Ատենի*; this is the first measurement on the
Տօնացոյց.

## Candidates

- **Qwen-VL fine-tune:** not built. Out of scope until the comparison says the VLM route
  is worth training for (Gemini zero-shot is the cheap proxy).
- **Licences:** evaluation only. Calfa models are CC BY-NC (settled, non-commercial use);
  Surya weights are RAIL-M (fine for research use).

## Method

1. **Same pixels for everyone.** `export_crops.py` writes each test line's crop with
   `dev/line_review/crops.line_crop` (the crop the human transcribed from) to
   `runs/ocr_eval/crops/<line id>.png`. Every engine reads those files.
2. **Predict on every sampled line, score the transcribed ones.** Each engine runs once
   over all of `sample.json`'s picks, so scores update as transcription continues without
   re-running engines. Output: `data/ocr_predictions/<engine>.json` (committed),
   `{engine, settings, generated_at, lines: {line id: text}}`.
3. **Score** (`score.py`, `jiwer`): character error rate per engine, pooled over lines
   (total edits / total reference characters). Before comparing, both sides are NFC
   normalized, whitespace is collapsed, and look-alike punctuation is folded
   (`-`/`֊`/`‐`, `.`/`․`, `:`/`։`, Phase 10's rule). Raw (unfolded) CER is reported too.
   Lines marked `illegible` or `bad-crop` are skipped. A third column ignores whitespace
   entirely: spacing around punctuation is ambiguous on this print (Gemini Pro writes
   `Բ . 11 .` for `Բ. 11.`).
4. **Breakdowns:** per stratum (`vol1-body`, `vol2-body`, `display`, `drop-cap`), and
   lines with vs. without the abbreviation mark ՟ (Phase 2b found a 3× gap there).
5. **Uncertainty:** a 95% bootstrap interval over lines for each CER. With tens of lines,
   intervals will overlap; the table says so rather than ranking on noise.
6. **Noise floor:** once rechecks exist, the CER between the two human passes. Engine
   differences smaller than it don't count.
7. **Report:** `reports/phase11_ocr_comparison.md`, regenerated by `score.py`: the table,
   the breakdowns, and the worst lines per engine for error analysis.

## Results

### First run (2026-10-05) — provisional, 12 lines

12 transcribed lines (382 characters), **all `vol1-body`**: the transcription queue served
picks stratum by stratum, so only the easiest stratum had been typed. It now serves picks
in rank order, which mixes strata.

| engine | CER | 95% interval | spaces ignored |
|---|--:|--:|--:|
| `paddle-calfa-tiny` | 0.0% | 0.0–0.0% | 0.0% |
| `tess-calfa-n` | 0.0% | 0.0–0.0% | 0.0% |
| `tess-grabar` | 0.5% | 0.0–1.2% | 0.6% |
| `gemini-pro` | 6.3% | 2.9–10.2% | 0.9% |
| `gemini-flash` | 7.1% | 4.2–10.5% | 0.9% |
| `trocr-ft` | 8.6% | 2.2–21.6% | 7.6% |
| `dots-mocr` (run 2026-10-05, same lines) | 12.3% | 7.4–18.8% | 11.8% |
| `surya` (run 2026-10-05, same lines) | 28.8% | 17.8–45.7% | 28.8% |

- **Both Calfa engines read clean Vol I body text perfectly**, character for character
  the same as the human (including the same `.`/`-`/`։` choices). The corpus's garble came
  mostly from bad line slicing, which verified lines remove.
- **Gemini's errors are mostly spacing** (`Բ . 11 .` for `Բ. 11.`), plus a few case slips
  (`եբր` for `Եբր`). With spaces ignored, both score 0.9%.
- **TrOCR (trained on the other book) breaks on display capitals** (p.453: `ՍԿԶԲՆԱՒՈՐԵԱԼ` →
  `Սէ Ձ բչ ս Լ Լ ո Ո է սւ`) and drops or swaps letters at line ends.
- **Surya hallucinates across scripts**: Armenian read as look-alike Latin
  (`Քանզի երեւեցաւ` → `Pwńgh hpbcbgmc`), the failure GlotOCR Bench reports for most open
  VLMs on Armenian. Full-page mode on a line crop was worse (it returned a table), so it
  runs in block mode.
- **dots.mocr (best open model on Armenian in GlotOCR) is mid-table here: 12.3%.** It
  swaps similar letters (`Քանզի` → `Բանզի`, `վ` → `ղ`, `Եբր` → `երր`) and mixes Latin
  into display capitals (`ՍԿԶԲՆԱՒՈՐԵԱԼ` → `U49FնԱհՈրեԱL`): 1915 Bolorgir is far from
  GlotOCR's rendered modern fonts. Runs locally via MLX (bf16, ~1 s a line).
- **Nothing is decided.** Body text doesn't separate the top engines; the display,
  drop-cap and Vol II lines (and the abbreviation mark ՟, absent from these 12) will.

Operational notes: Gemini Pro takes ~25 s a line and its API returned 504s under load
(one line still failed after 3 retries, retried on the next run); the runner sends 8
lines at a time. Surya runs on llama.cpp (installed 2026-10-05); the first call loads the model (~5 min), then ~0.6 s a line.

### Ceiling of the Calfa engines (2026-10-08, sample built, typing under way)

The 12-line result (both 0%) was the luck of a small, easy sample. Both engines were run
on **every line of the book** (14,388 lines; verified lines where they exist, otherwise the
`paddle-filled` baseline with fixes so far): `dev/ocr_eval/ceiling.py`.

- **They disagree on 36.6% of lines** (5,264), **2.2% of characters**. Only 94 differ just
  in spacing. The rest are look-alike Bolorgir letters: Չ/Ձ/Զ (600+, mostly large line
  initials), չ/շ, զ/ղ, է/ե, գ/դ, and `3` or `)` for ձ. Where they disagree, at least one is
  wrong, so **their line error rates sum to at least 36.6%** and their CERs to at least
  about 2.2%: roughly 1–2% CER each, i.e. an error every few lines, not a near-perfect
  read.
- **Sample** (`data/transcriptions/ceiling/sample.json`, served at `/transcribe?set=ceiling`):
  300 random disagreements + 200 random agreements, 164 pages, half Vol I, half Vol II.
  Each engine's line error rate = the two groups' rates weighted by their share of the
  book; lines-per-error is its inverse, with a bootstrap interval
  (`reports/phase11_ceiling.md`). Agreements also catch identical mistakes by both.
- Test-set transcriptions of verified lines are reused, not retyped. Lines from
  unverified pages carry baseline keys (`p520~line_013`), not stable ids; a box that clips
  the text is marked Bad crop and left out.

### LLM correction of the Calfa output (2026-10-09, built; awaiting typed lines)

Target (maintainer): **> 90% of lines error-free**; below that, correcting lines costs
more than typing them. Phase 5 found Gemini 3.1 Pro the best and cheapest corrector and
Opus comparable, with GPT-5.5 over-correcting and strict rules essential.

`dev/ocr_eval/correct.py` sends each page with **both engines' readings** where they
disagree (`A: … ‖ B: …`) and one reading where they agree, under Phase 5's v2 rules
adapted to two readings. Candidates: `claude-opus-5-5`, `gemini-3.1-pro-preview`,
`gemini-3.8-flash`, `gpt-6.1-sol` (Gemini 4 isn't reachable with this API key yet:
`gemini-pro-latest` still serves 3.1 Pro). Opus calls carry the server-side refusal
fallback (`fallbacks: "default"`, sent via `extra_body`: the repo's anthropic SDK 0.107
predates the parameter).

Smoke test on p.615 (86 lines, 42 with two readings): all four parse cleanly and agree
on the clear cases (`ԴՁՉ`/`ԴՁ` → `ԴՁ`, `Գչշ`/`Գշ` → `Գշ`, `բ)`/`բձ` → `բձ`); Opus, Gemini Pro
and Flash change no agreed line, GPT 6.1 changes 2. Per page: Opus 26 s (~$0.08),
Gemini Pro 33 s, Flash 11 s, GPT 6.1 31 s.

Scoring (`ceiling.py score`) rates every engine, correctors included, by error-free
lines weighted back to the book, with a bootstrap interval and a count of lines a
corrector broke (both OCR engines right, corrector wrong).

#### Prompt A/B: v2 vs v3 (maintainer's idea, 2026-10-09)

v3 = v2 + **this book's common errors with examples**, mined from the engines'
disagreements over the whole book (every example word also occurs outside both test
samples, so the A/B isn't scored on lines the prompt quotes). It names: tone codes
(letter-numeral + Ձ/ձ, misread as Չ/Զ/3/)), weekday codes (letter-numeral + շ, misread as
չ by *both* engines), շ/չ inside words (Ճաչու → Ճաշու), Տէս → Տես, Քարող → Քարոզ, տեղաոյս →
տեղւոյս, no Latin letters, and a warning that Չ/Զ are right in Չորրորդ, Զկնի, Զատիկ.
Unlike v2, v3 lets these patterns be fixed even where both readings agree: 15 agreed
lines have a weekday code with չ, 19 a tone code with Չ/Զ/3/), 12 read Ճաչու.

**Test:** the same model, both prompts, the same pages; compare error-free lines and
lines broken on the typed ceiling lines (`--prompt v3` → engine `corr-<model>-v3`).
**Open:** whether the print has ՚ before standalone ի (Paddle reads `'ի` 274 times,
hye-calfa-n never); left out of v3 until confirmed.

| v3 + `՚ի` rule | **93.7%** | 88.5–98.8% | 0 |
| v2 + `՚ի` rule | 92.7% | 87.8–97.6% | 0 |
| v3 | 81.6% | 72.5–89.7% | 0 |

- **The missing ՚ before standalone ի was most of what was left**: 8 of v3's 13 wrong
  lines, 6 of them where both engines agree. The print has ՚ before standalone ի
  (maintainer; 10 of 10 in the first 87 typed lines), so `dev/ocr_eval/rules.py` adds it
  deterministically after correction, written as `<engine>+rules`. Neither prompt made the
  model add it.
- **With the rule, correction clears the 90% target**; the interval's lower end (~88%)
  needs more typed lines to confirm.
- **v3 vs v2: not settled.** v3 was right on 2 more disagreement lines; on 1 agreed line
  where both engines read `ճըդ-` (print `ճըգ-`), v2 fixed it and v3 left it. Neither broke
  a correct line. A paired comparison needs more lines.
- v2's run echoed the `A: … ‖ B:` markers on 2 lines; `parse` now treats such lines as
  fallbacks.

**Typing target** (maintainer, 2026-10-09): about 60 disagreements and 90 agreements, not
the full 300 + 200. That narrows the interval to about ±3.5 points, enough to tell whether its
lower end clears 90%. Keep watching v3 vs v2 as lines are added.

#### v4: line images for the disagreements (maintainer's idea, 2026-10-09)

v4 = v3 + the scanned crop of every line where the engines disagree (the same
`crops.line_crop` the engines read), sent after the text and labeled `Line <n>`. Agreed
lines stay text-only, which keeps cost down: the image is for the look-alike calls
(Ձ/Չ/Զ, շ/չ) that the meaning can't settle. It is scored against v2 and v3 on the same pages
(`--prompt v4` → `corr-<model>-v4`).

agreements).** Em dash `—` is now folded with `-` in scoring, like the other look-alike

#### Planned: review buckets (maintainer, 2026-10-09)

Every line will still go to a human for final review. The pipeline sorts lines into
buckets so the reviewer can move quickly through the likely-correct ones and spend
attention where the machine is least sure. Candidate signals:

- **likely correct**: both engines agree and the corrector left the line unchanged;
- **possible error**: the engines disagree and the corrector chose one reading, or the
  corrector changed an agreed line;
- **likely error**: the corrector's output matches neither reading, or it changed more
  than one or two letters, or the line has a low-confidence stratum (display type, drop
  cap, bad crop).

Each bucket's actual error rate is measured on the typed ceiling lines before the
thresholds are trusted. Not built yet.

## Open OCR VLMs: feasibility (desk check, 2026-10-05)

Not run; from published benchmarks. **Armenian is the deciding fact, not model size.**

- **GlotOCR Bench** (2026; 100+ scripts, *rendered modern fonts*, not 1915 Bolorgir) on
  Armenian: Gemini 3.1 Flash-Lite 97% of sentences within 5% CER, dots.mocr 95%,
  dots.ocr 93%; **most open models ~0%, including Qwen3-VL-8B**, which hallucinates other
  scripts. That matches Surya here (Armenian read as look-alike Latin).
- **Leaderboards measure something else.** OmniDocBench and olmOCR-Bench are dominated by
  Latin/CJK documents; small specialists (PaddleOCR-VL-1.6, TeleOCR ~1B) beat
  Qwen3-VL-235B there, which says nothing about Armenian.
- **What fits this Mac (M1 Pro, 32 GB)** through MLX: dots.ocr/dots.mocr (~3B, ~6 GB bf16;
  `mlx-community/dots.mocr-bf16` exists), Qwen3-VL-8B (4-bit ~5 GB), Qwen3-VL-32B or
  Qwen3.6-35B-A3B at 4-bit (~18–20 GB, slow). What doesn't: Qwen3-VL-235B-A22B (~130 GB
  even at 4-bit: a multi-GPU cloud box or a 192 GB Mac Studio).
- **Qwen would need fine-tuning to be useful** (zero-shot ~0% on Armenian). The Manchu
  study (arXiv 2507.06761) took Qwen2.5-VL from ~25–30% to ~5–8% CER with LoRA on 1,000
  synthetic images, and it transferred to real documents. LoRA on a 7–8B model is a few
  GPU-hours on one rented 48–80 GB card; on this Mac, MLX LoRA is possible but slow.
- **Expected gain is narrow.** The Calfa engines already read clean body text at 0%
  here. A VLM can only help on what's left: display type, drop caps, abbreviations,
  damaged print, Vol II. Its language prior cuts both ways: it can recover damaged letters,
  but it also "fixes" spelling and case (Gemini's `եբր` for `Եբր`), which a literal corpus
  must not have.
- **dots.mocr was then run** (see Results): 12.3%, behind the Calfa engines. Decide on a Qwen fine-tune only if the full test set shows the Calfa engines
  failing on the hard strata.

## Gate

- Phase 10's gate is met (300 lines, rechecks done).
- All candidates scored on the same lines; table, intervals and noise floor recorded here.
- One engine (or ensemble) chosen for the re-OCR, with the reason in a decision log.

## Out of scope

Fine-tuning on the Տօնացոյց, LLM post-correction, and the re-OCR itself.
